# 架构设计

<Callout type={'warning'}>
  本页以当前中文文档和代码为准。对应英文文档未同步本项目的定制行为，可能已经落后。
</Callout>

本项目采用 Next.js 服务端与 Vite SPA 组合的 Monorepo 架构。Next.js 负责服务端、认证和 SPA HTML 输出，React Router DOM 负责主应用的客户端路由，核心 Runtime 与数据访问能力沉淀在共享包中。

## 总体分层

```plaintext
Browser / Electron / CLI
          |
          v
React UI + React Router DOM
          |
          v
Zustand Store + SWR
          |
          v
Client Service + tRPC Client
          |
          v
Next.js Route Handler / tRPC Router / WebAPI
          |
          v
Server Service + Agent Runtime
          |
          v
Database Model / Repository
          |
          v
PostgreSQL + Redis + S3
```

## Web 与路由架构

| 边界                 | 位置                    | 当前职责                                  |
| ------------------ | --------------------- | ------------------------------------- |
| Next.js App Router | `src/app/`            | 认证页、API、tRPC、WebAPI、文件服务和 SPA HTML 模板 |
| SPA 入口             | `src/spa/entry.*.tsx` | Web、移动端、Electron、弹窗入口                 |
| SPA 路由树            | `src/spa/router/`     | React Router 路由配置                     |
| 页面根节点              | `src/routes/`         | layout、page 和动态 segment               |
| 领域功能               | `src/features/`       | 页面主体、业务组件和领域 hooks                    |
| 全局 Provider        | `src/layout/`         | 认证、主题、状态初始化和全局上下文                     |

认证和需要服务端渲染的页面由 Next.js 处理；聊天、设置、资源、社区、生成和管理后台等高交互页面由 SPA 承载。

当前桌面端的关键路由语义：

- `/`、`/explore`：都渲染独立全屏门户，不使用聊天工作台布局
- `/home`：聊天工作台
- `/home/agent/*`、`/home/group/*`、`/home/resource/*`、`/home/settings/*`：工作台内功能
- `/home/settings/admin`：集成在现有 SPA 中的管理后台，由 RBAC 守卫控制

移动端没有完全复用桌面端门户语义，不能仅依据桌面路由推断移动端行为。

## roots 与 features

新路由必须遵守以下边界：

```plaintext
src/spa/router/       注册路径和嵌套关系
        |
        v
src/routes/           薄 route root，只组合页面和 layout
        |
        v
src/features/         领域 UI、hooks 和业务组件
```

仓库仍保留大量历史 `src/routes/**/features` 目录，这是迁移债务而不是推荐模式。新功能不要继续在路由目录中创建业务 feature。

桌面端 Web 和 Electron 路由分别来自：

- `src/spa/router/desktopRouter.config.tsx`
- `src/spa/router/desktopRouter.config.desktop.tsx`

两份配置必须保持路径和嵌套同步，`desktopRouter.sync.test.tsx` 用于守护这一约束。

## 客户端状态与数据获取

- `src/store/` 使用 Zustand 管理客户端状态和 action。
- `src/services/` 封装客户端 tRPC/API 调用。
- SWR hook 负责请求去重、缓存和重新验证。
- 组件通过 selector 消费状态，避免订阅整个 Store。

典型写入链路：

```plaintext
UI -> Store Action -> Client Service -> tRPC Router
   -> Server Service -> DB Model / Repository -> PostgreSQL
```

## 服务端架构

| 层                    | 位置                                 | 约束                                                    |
| -------------------- | ---------------------------------- | ----------------------------------------------------- |
| REST / Route Handler | `src/app/(backend)/api/`、`webapi/` | Webhook、流式响应和特殊 HTTP 接口                               |
| tRPC 入口              | `src/app/(backend)/trpc/`          | 将 HTTP 请求接入 Router                                    |
| tRPC Router          | `src/server/routers/`              | 校验输入、鉴权并调度服务                                          |
| Server Service       | `src/server/services/`             | 可访问数据库的服务端业务                                          |
| Server Module        | `src/server/modules/`              | 不访问数据库的纯模块                                            |
| 数据层                  | `packages/database/`               | `src/` 下的 schemas、models、repositories，以及根级 migrations |

tRPC Router 按运行形态分为 `lambda`、`async`、`mobile` 和 `tools`。新增接口前应先找到同领域 Router，而不是另建平行 API 风格。

## Agent 与模型 Runtime

`packages/model-runtime/` 统一各模型 Provider 的协议差异。`packages/agent-runtime/` 位于其上，负责 Agent 循环、工具调用、上下文处理、人机介入和多 Agent 编排。

工具体系分为：

- `packages/builtin-tool-*/`：单个工具的 manifest、executor、状态和 UI 协议。
- `packages/builtin-tools/`：集中注册工具、渲染器、检查器和介入逻辑。
- `src/store/tool/`：客户端工具状态与执行接入。
- `src/server/services/agentRuntime/`：服务端 Agent Runtime 接入。

## 认证、权限与商业定制

- Better Auth 提供认证能力，入口集中在 `src/auth.ts` 和 `src/app/(backend)/api/`。
- 管理后台使用现有 RBAC 权限体系，不是独立部署的应用。
- 商业开关和平台托管模型配置由 `src/envs/app.ts`、`src/server/globalConfig/` 与相关 business 模块接入。
- 助理管理隐藏只发生在 UI 和路由守卫层，Agent 数据关系与聊天 Runtime 不会因此消失。

修改这些区域前必须阅读 `CONTEXT.md` 与 `docs/adr/`，避免破坏已确定的业务语义。

## 数据存储

| 存储         | 用途                     | 本地实现                      |
| ---------- | ---------------------- | ------------------------- |
| PostgreSQL | 用户、会话、消息、Agent、计费等持久数据 | ParadeDB PostgreSQL 17 镜像 |
| Redis      | 缓存和运行时状态               | Redis 7 Alpine            |
| S3         | 文件、图片和知识库对象            | RustFS                    |

Drizzle schema 位于 `packages/database/src/schemas/`。数据库变更必须使用仓库的 Drizzle 与 migration 约定，不能手写一份未纳入迁移序列的临时 SQL。

## 构建架构

Web 构建不是单一步骤：

```plaintext
Vite build
  -> dist/desktop 或 dist/mobile
  -> build:spa:copy
  -> public/_spa + spaHtmlTemplates.ts
  -> Next.js build
```

因此 `bun run build:spa` 只验证 SPA 产物；要验证 Next.js 能提供最新 SPA，还必须执行 `bun run build:spa:copy`，完整流程使用 `bun run build`。

更多接手注意事项和当前风险见 [项目接手与维护指南](/zh/docs/development/basic/handoff)。
